## Faults (first)

### 1. The activation link in the sign-up email breaks for any address with a "+" (sure about the cause)
- **Where:** `lambda-sync/stockiq-cognito-email-sender/lambda_function.py` line 16 puts the address into the link as it is:
  `...signup.html?activate=true&code={code}&email={email}`. The page reads it with `URLSearchParams` (`website/signup.html`
  line 885), which turns a "+" into a space. An address such as `name+shop@gmail.com` becomes `name shop@gmail.com`, and the page
  asks Cognito to confirm a user that does not exist.
- **What a visitor sees:** "Activation failed: User does not exist." (or similar), straight after signing up for the free trial.
  The notes say the link "works 100%", true only for addresses without a "+" (a common Gmail habit).
- **Second fault, same path** (`signup.html` lines 953-958): the friendly branch "This account is already activated. Please
  log in." is chosen by looking for the text "already confirmed" or "Invalid code" in Cognito's error. Cognito's own words are,
  as far as I know, "User cannot be confirmed. Current status is CONFIRMED" and "Invalid verification code provided, please try
  again", which contain neither. So someone who clicks the link twice, or mistypes a code, gets a raw error in an alert box. I
  have not been able to trigger a real Cognito answer from here, so this part is "probably".
- **The change:** `urllib.parse.quote(email, safe='')` in the Lambda (it already imports `urllib.parse` and never uses it); in
  `signup.html` match Cognito's real messages ("Current status is CONFIRMED", "Invalid verification code") and say what to do
  next in plain words. Test with a "+" address in `check-tools` against the page's own code, no real account needed.
- **Why it matters:** this is the one step every new member must pass; each loss here is a sign-up that never reaches the
  autopilot. Proposal on the Admin page.

### 2. A member who is not the owner would see a false "Needs you" about email (sure about the code, unsure how many accounts)
- **Where:** `stockiq-ai-trader` `send_mail` (line 2764) sends through SES; SES on this account is still in the sandbox
  (`stockiq.md`: production access refused), so it sends only to addresses the owner has verified. Any other address is refused
  (`MessageRejected`). `note_mail` stores that, and `needs()` (line 3628-3630) then shows, for every account with the "email me"
  switch on (the default, `settings.get('emails', True)`): *"Its last email could not be sent (MessageRejected). What it would
  have said is under 'What it has done'."* and puts a ⚠ on the dashboard's AI autopilot tab.
- **Who gets it:** since 24 Oct the free trial includes the autopilot, so every trial and paying member who has not turned the
  switch off gets an email attempt at each shared note or progress report, and then this box. The member can do nothing about
  it (only the owner could verify an address). It reads as a fault of the product on the first week of a trial.
- **The change:** treat a refusal for an unverified address as "emails are not available for this account yet": switch the
  setting off for that account quietly, show no "Needs you" item and no ⚠, and say once, in the switch's own line, "Email
  reviews are not available yet; everything is also under What it has done". Keep the item for the owner's listed accounts, where
  a refusal would be a real fault. Add a test in `ai_trader_test.py`.
- Related and unchanged: the home page's "Get Screener Highlights by Email" box, which cannot send for the same reason; the
  register says it starts when search traffic appears (`screener-email`). The confirmation text there is honest ("when the email
  starts"). When the email is built it needs a signed one-click unsubscribe: `unsubscribe_email` in `stockiq-email-capture`
  takes any address with no proof, so anyone could unsubscribe anyone.
