## Faults, most serious first

### 1. Anyone who knows a paying member's email can cancel their real Stripe subscription (sure)
- **The cancel path checks nothing.** The dashboard's "Cancel Subscription" button does two things:
  1. It asks the dashboard function for the subscription ID, sending `get_subscription_id` with whatever email the browser
     gives (`lambda-sync/stockiq-dashboard/lambda_function.py` line 938: it reads `<email>#registration` and returns
     `stripeSubscriptionId`).
  2. It sends that ID to the payment function as `cancel_subscription`, which runs `stripe.Subscription.delete(id)` with no
     other check (`lambda-sync/stockiq-payment-handler/lambda_function.py` line 384).
  Both addresses are public, written in `dashboard.html`. So two requests from anywhere cancel any member's real paid
  subscription.
- The notes accept "the userId is whatever the browser sends" because, until now, that only touched fake money. This
  touches **real money and real customers**: it stops revenue, and it also triggers the 30-day deletion of the member's data
  (fault 2's last point).
- **The payment function also takes fake Stripe events.** A POST with `action: "handle_webhook"` is handled as if Stripe had
  sent it. There is no signature check (line 30, and the comment at line 130: "without signature verification for now").
  For example, someone whose subscription has ended could replay a `checkout.session.completed` with their own old
  subscription and be marked active again.
- **Fix (one session, one function and one dashboard line):**
  - Check Stripe's signature on every event (`stripe.Webhook.construct_event` with the endpoint's signing secret, kept in
    the function's settings), and remove the `handle_webhook` action.
  - Make `cancel_subscription` find the subscription itself, from a verified sign-in: check the Cognito ID token the
    browser already holds against the user pool's public keys. Never take a subscription ID from the request.
  - Stop `get_subscription_id` returning the ID to the browser.
- Today the only paying account is the owner's, so nothing has been lost. It must be closed before the first real customer.

### 2. Changing plan marks the member as cancelled and schedules their data for deletion (likely; read from the code, not seen live)
- "Upgrade to Pro" or "Downgrade to Starter" on a paid account opens a **new** Stripe checkout. When it completes,
  `handle_subscription_created` deletes the old subscription (line 175), then writes the new plan as active (line 227).
- Stripe then sends `customer.subscription.deleted` for the **old** subscription. `handle_subscription_cancelled` (line 347)
  looks the member up by the customer's email and does not check *which* subscription ended. So it:
  - sets the record to `cancelled`, and
  - asks the dashboard function for the 30-day deletion of the member's data (`set_subscription_end_ttl`).
  The member keeps access until the date shown, but the dashboard then says "Subscription cancelled. Access expires on …"
  and hides the Cancel button (`dashboard.html` line 3961). They cannot cancel the plan they are actually paying for, except
  by contacting support.
- A downgrade also throws away the rest of the month already paid on the higher plan: the old subscription is deleted
  outright, with no proration.
- **Fix:**
  - In `handle_subscription_cancelled`, ignore an event whose subscription is not the record's `stripeSubscriptionId`.
  - Better still, change plans with `stripe.Subscription.modify` (Stripe prorates by itself, and the existing
    `handle_subscription_updated` already records the new plan) instead of a second checkout.
- The wording also says "Downgrade" on a red button, as if it were a danger: plain "Switch to Starter" reads better.
